# Pallas Kernel Corpus

A source corpus of directly runnable **TPU-only** JAX/Pallas kernels collected
from JAXBench, PallasBench, MaxText, Tokamax, vLLM TPU Inference, and sglang-jax.

## Layout

```text
kernels/
  <category>/
    <kernel_family>/
      baseline.py
      jaxbench_optimized.py
      pallasbench_optimized.py
      maxtext_optimized.py
      tokamax_optimized.py
      tpu_inference_optimized.py
      sglang_jax_optimized.py
```

Only files that exist for a family are present. A source file may contain
forward, backward, or hardware-tuned variants when upstream keeps them as one
implementation. The PallasBench directories are the exception to one file per
repository: PallasBench splits what other repos fuse, so a directory there
holds one `pallasbench_<task>_optimized.py` per task —
`kernels/elementwise/activation/` has five, one each for `gelu`, `relu`,
`sigmoid`, `silu` and `tanh`.

There are intentionally no `upstream/`, `adapters/`, or `environments/`
directories:

- each optimized file contains the implementation and any repo-local helpers it
  needs;
- optimized files do not import their original repository package;
- each file exposes a callable `kernel` (or documents multiple named entry
  points) and a `SOURCE` metadata dictionary. Eleven of the 108 also carry a
  `python file.py` smoke runner, inherited from upstream; that was an early
  convention rather than a corpus-wide one, and the test suite is what actually
  exercises every file;
- each family has a JAX `baseline.py`; when upstream implementations use
  different semantics, the baseline exports one explicitly named contract per
  semantic interface. Four directories carry an additional
  `<source>_reference.py` beside it, for a reference that is a *carried
  upstream file* rather than a corpus-written one — Tokamax's and JAXBench's
  own reference modules, sglang-jax's contract read off its only call site, and
  the DeepSeek-V4 cache readers. Keeping those separate is not cosmetic: the
  PallasBench `baseline.py` files are generated by
  `tools/flatten_pallasbench.py`, so anything hand-added to them would be
  overwritten on the next regeneration.

## Counting

`inventory.json` is the authoritative ledger. Its launch-point rows are
re-derived from the pinned upstream trees by walking every Python AST, not
asserted:

```bash
python tools/audit_launch_points.py --checkouts <dir-with-pinned-trees> \
  --output launch_points.json
python tools/build_inventory.py --audit launch_points.json
```

The pinned snapshots contain **151 kernel source files**, **181 Pallas launch
points**, and **40 semantic families**. Removing Mosaic GPU and Pallas-Triton
implementations leaves **156 TPU-compatible launch points**:

| Source | Launch points | TPU-compatible |
|---|---:|---:|
| JAXBench | 17 | 17 |
| PallasBench | 45 | 45 |
| MaxText | 14 | 14 |
| Tokamax | 39 | 15 |
| vLLM TPU Inference | 39 | 39 |
| sglang-jax | 27 | 26 |
| **Total** | **181** | **156** |

These counts are deliberately kept apart, because they are not interchangeable:

| Count | Value |
|---|---:|
| Source files in scope | 151 |
| TPU launch points audited (migration *candidates*) | 156 |
| **TPU launch points migrated and validated** | **136** |
| Semantic families with any migration | 34 of 40 |
| Corpus directories | 34 |

156 is an inventory of what exists upstream. 136 launch points have been made
standalone and checked for correctness on TPU; 39 of those are also profiled.
The 2 `rpa_v3` kernels are deliberately left unprofiled because no upstream
benchmark defines a native shape for that contract and inventing one would be
worse than reporting none, and the 43 PallasBench kernels are unprofiled
because PallasBench ships its own benchmark harness and re-measuring them under
this corpus's tracing flags would produce a second, worse set of numbers for
kernels whose upstream already reports them.

Profiling the MLA family used to fail on the validation host, for every
implementation including the ones with a recorded `result.json`. Two separate
tracer limits were responsible, neither of them anything to do with the donated
`cache_kv` that was the obvious suspect: batching iterations into one trace
overran xprof's 1,000,000-event trace-viewer cap, and running the correctness
check, the cost analyses and the wall-clock loop *before* the trace loop left
the TPU tracer able to open only one profiling session per process. This kernel
is dense enough under the corpus's instruction-level tracing flags to hit both.
`tools/profile_kernel.py` now traces one iteration per chunk by default, runs
the traced measurement before any other work, and reports which limit a short
trace hit. See `profiles/native/mla_attention/report.md` §7.

Most migrated launches are forward passes. **Backward passes are covered in
three families**: splash attention (backward-dQ and backward-dKV from both
JAXBench and MaxText), flash attention (JAXBench dQ/dKV plus Tokamax's splash
dKV), and grouped matmul (JAXBench's `tgmm` plus `tgmm_v2` from MaxText and
Tokamax), and **cross entropy** (Tokamax's
`linear_softmax_cross_entropy_loss`, both directions). **No backward launch
point is open**: the only unmigrated ones are the v1 `tgmm`s, deliberately
deferred on qwix.

**No family the corpus has started has open work left** — all 34. In each,
every audited TPU launch point is either migrated and validated, or recorded
with evidence as a duplicate, a deliberate deferral, a kernel that does not do
what its name suggests, or — new with `speculative_decoding` — a kernel that
**does not run upstream either**. **All 5 remaining open launch points are in
the 6 families the corpus has not touched.**

The TPU-compatible total was **157 until `paged_attention` was migrated**, and
the correction is worth naming: sglang-jax's paged attention is a GPU kernel
that the AST audit had been counting as a TPU candidate. It passes
`plgpu.CompilerParams` unconditionally and its own test file says "This test
suite is designed to be executed on GPU", but its import is spelled `from
jax.experimental.pallas import triton as plgpu`, and the audit's backend check
scanned for the *dotted* form `jax.experimental.pallas.triton`, which never
appears in that text. `tools/audit_launch_points.py` now reads the parsed
imports instead. Exactly one launch point was affected — every other GPU file
gives itself away in its path — but the check was the blind spot, not the
kernel.

## Auditing the ledger

`migrated_launch_points` and the `correctness: PASS` beside it are only as good
as the check behind them, and twice a launch point was counted while nothing
exercised it: grouped matmul's `tgmm_v2`, flattened alongside `gmm_v2` and
recorded as a migrated *backward* pass with no test differentiating it, and
flash attention's PallasBench kernel, whose PASS came from the profiling run
rather than the suite. A third case was worse: two SparseCore gather-reduce
kernels had tests that passed **against their own XLA fallbacks** — at the
shapes chosen, `is_compatible` or a VMEM threshold sent the call to plain JAX,
so the comparison was JAX against JAX and agreed trivially.

`tools/launch_coverage.py` makes that check repeatable. It runs the suite with
a wrapper around `pl.pallas_call`, `pl.kernel` and `pl.core_map` that records
the source file and qualified name of every kernel body launched, then reports
any corpus file with launch sites that never fired:

```bash
uv run --frozen --with pytest python tools/launch_coverage.py
```

It needs a TPU and takes about as long as the suite, so it is a step to run
when adding an implementation, not on every edit. The related rule — that a
correctness pass does not prove the kernel ran — is the same one
`profile_kernel.count_pallas_launches` enforces, and the gather-reduce tests
now assert the launch count directly on both sides of each fallback boundary.

A green assertion is separately not evidence if what it compares is degenerate.
`tools/assertion_strength.py` sweeps for that, with a mechanical criterion
rather than a judgement call:

> a comparison is **vacuous** if a kernel that returned all zeros — or one
> constant everywhere — would still pass it.

It intercepts `assert_allclose`, `assert_array_equal` and the per-module
`cosine` / `_close` helpers, which between them are every numeric comparison the
suite makes, and reports the ones a degenerate output would satisfy. The worked
example is DeepSeek-V4's sliding-window MLA: its attention sinks are drawn from
[200, 500] while the logits reach ~135, so `exp(sink − m)` swamps the softmax
denominator and **every output on both sides collapses to ~1e-26**. Three
`assert_allclose(rtol=0.1, atol=0.1)` calls were comparing two arrays of zeros.
The sweep also found the `m` comparison in that family's decode step passing at
a tolerance its own mean would satisfy.

Both are fixed: `m` is now asserted bitwise and `L` at 1e-5, since both come
back near-exact, and the output comparison asserts *which regime it is in* —
degenerate or not — rather than running an allclose that zeros would satisfy.

The sweep grew a third category when Tokamax's cross-entropy arrived. A 0-d
reference *is* its own mean, so "a constant output would pass" is true of every
scalar comparison and says nothing — reporting those as weak would bury real
findings under a category error. But the question a scalar does raise is worth
asking: a loss reduced to one number is a thin check on a kernel that computed
`B × V` logits to produce it. So scalars are reported only when **no other
comparison in the same test covers an array**. All four of the corpus's scalar
comparisons are backed that way, by the `lse` vector returned alongside the
loss.

Migrating `layout_transpose` then exposed a blind spot in the sweep itself,
which is worth more than the finding that came out of it. `_stats` skipped any
array failing `np.issubdtype(dtype, np.number)` — and ml_dtypes' `bfloat16` and
the fp8 types, which are what a good half of these kernels actually return, are
registered with kind `"V"`. That test is **False** for them. So every comparison
made directly on a bf16 or fp8 array had been dropped without a word, and the
sweep reported "clean" while not looking at them. The gate is now the real
question — whether the array converts to float64 — and the count went from 274
to 301: 16 of those are the new transpose family's, and **11 were comparisons
elsewhere in the corpus that had been invisible all along**. All 301 pass.

That is the same failure this tool exists to catch, one level up: a check that
reports success because it never ran. It is why `launch_coverage.py` prints its
own blind spots rather than only its findings.

Run it with:

```bash
uv run --frozen --with pytest python tools/assertion_strength.py
```

The last complete sweep recorded **311 comparisons, none of which a zero or
constant output would pass and none resting on a scalar alone** — and it earned
its keep on that run by catching a vacuous comparison in the then-new
`fused_moe` tests, where upstream's flat `atol=2e-1` sat above an output peaking
at 0.096. That is fixed (the tolerance is now relative to the reference's
magnitude) and the fixed file passes, but see **Verification status** below for
what has and has not been re-run since.

Several audited launches are deliberately **not** migrated because they are the
same kernel as one already in the corpus, which the ledger records with a
reason rather than counting twice: JAXBench's `3p_MLA_Attention` is its
`1p_Flash_Attention`, and its `4p_Sparse_Attention` is its `2p_GQA_Attention`.

A launch point is not a file: one upstream implementation can contain a
forward, a backward-dQ, and a backward-dKV launch.

## Verification status

Every kernel counted in `inventory.json` was validated on a **TPU v6e-1**, and
each family's own test file passed on that machine at the time it was added.
That machine is no longer available, which changes what this repository can
claim, so the state is recorded here rather than implied:

| Check | Status |
|---|---|
| Per-family test files | Each passed on TPU when its family was added, including the two most recent (`speculative_decoding`, `paged_attention`) |
| Full suite, end to end | Last confirmed green at **433 passed, 1 skipped**, before the `fused_moe` tolerance fix and before `speculative_decoding` and `paged_attention` were added |
| `tools/launch_coverage.py` | Last run before those same three changes |
| `tools/assertion_strength.py` | Last complete run recorded 311 comparisons, all clean, before those same three changes |

The three changes not covered by a full-suite run are each covered by their own
file, which did pass: the `fused_moe` tolerance fix (11 passed), the
`speculative_decoding` family, and `paged_attention` (6 passed). What is missing
is the *regression* evidence that they did not disturb anything else, plus a
final pass of the two audit tools. The host became unreachable mid-run, and I
have not re-run them since; nothing here is asserted as green that was not
observed to be green.

Anyone with a TPU can close that gap:

```bash
uv sync
uv run --frozen --with pytest python -m pytest tests/ -q
uv run --frozen --with pytest python tools/launch_coverage.py
uv run --frozen --with pytest python tools/assertion_strength.py
```

Two further caveats hold regardless of hardware. Expert-parallel and
tensor-parallel kernels — `fused_moe`, `gated_mlp`, and anything ending in a
collective — were validated at **one device**, where the collective degenerates
to the identity; the surrounding fusion is exercised, the cross-device reduction
is not. And `collective_matmul` was never started, so its two launch points are
neither migrated nor assessed.

## Run

The corpus has no private runtime wrapper. Use any external Python environment
with a TPU-capable JAX installation:

```bash
python kernels/attention/flash_attention/baseline.py
python kernels/attention/flash_attention/pallasbench_optimized.py --interpret
python kernels/attention/flash_attention/jaxbench_optimized.py
```

Interpret mode is only a convenience for generic Pallas kernels that support
it. Mosaic TPU kernels must be executed on a TPU.

The three flash-attention files share a directory but not a contract: the
Tokamax file is a Splash kernel with pre-scaled Q and independent `Dqk`/`Dv`,
and the PallasBench file is a non-causal 2-D educational kernel. `baseline.py`
therefore exports one named reference per contract instead of a single
misleading API.

One caveat the flash family exposed, which applies corpus-wide: **a pure-JAX
reference can still lower to a `tpu_custom_call`.** `causal_bhsd` is plain
einsum + softmax, and XLA rewrites it into `%online-softmax`, a Mosaic custom
call. So "contains a tpu_custom_call" is not a test for "is a Pallas kernel";
`profile_kernel.XLA_AUTOMATIC_CUSTOM_CALLS` lists the rewrites to exclude.

The three grouped-matmul files do share one contract. Two caveats are recorded
rather than smoothed over: sglang-jax's kernel is *the same code* as
tpu-inference's (identical HLO, medians within 0.02%), and `jax.lax.ragged_dot`
is not a valid JAX baseline for this family because on TPU it lowers to Mosaic
`tpu_custom_call`s. See
[`profiles/native/grouped_matmul/report.md`](profiles/native/grouped_matmul/report.md).

**`grouped_matmul` is complete**: 10 of its 14 audited TPU launch points are
migrated and validated, and the other 4 are the v1 `gmm`/`tgmm` pair from
MaxText and Tokamax, deliberately deferred rather than take a qwix dependency.

MaxText and Tokamax also ship grouped matmuls. Only their **v1** kernels need
the third-party `qwix` package; their **v2** kernels need nothing extra and are
migrated, so all five upstream lineages are now represented with no change to
the pinned dependency set. The v2 kernels are also the fastest implementations
measured — they beat `jax.lax.ragged_dot` by 28% under uneven routing. Note
that v2 changed the default `preferred_element_type` from v1's `float32` to the
input dtype, which makes a drop-in swap a silent accuracy regression unless the
caller pins it.

**Four v2 forwards are migrated, and they are four different kernels.** MaxText,
Tokamax, sglang-jax and tpu-inference each ship one; pairwise, only 23–57% of
their shared definitions are AST-identical, so unlike the streamindex top-k next
door this is not vendoring. They agree bit-exactly on the contract. Only MaxText
and Tokamax ship a `tgmm_v2` beside the forward; sglang-jax's and
tpu-inference's are forward-only.

The **backward pass has a calling-convention trap** that went unnoticed until
this family was finished. Three launch points implement `tgmm`, and they split
on which axis of `lhs` is the contracted one: JAXBench's `tgmm` takes `lhs`
**already transposed**, `[k, m]`, while the megablox `tgmm_v2` kernels take
`[m, k]` and transpose inside. Both are 2-D float arrays, neither checks, and at
`m == k` the mistake is invisible. `baseline.grouped_matmul_transpose` is the
reference for both, and a test pins each pairing. Worth noting how the gap was
found: `tgmm_v2` was already counted as a migrated *backward* launch point for
MaxText and Tokamax, but no test exercised it — the launch point was present in
the flattened file and the ledger recorded it as migrated on that basis. All
three are now validated bit-exactly.

The ragged-paged-attention directory holds two contracts that are not
interchangeable: `rpa_v2` interleaves K/V in one paged cache and carries a
scalar sequence count, while `rpa_v3` appends K/V to a dtype-packed cache and
splits the batch with a `distribution` array. Even inside `rpa_v3` the two
implementations share a cache layout but not a signature — sglang-jax requires
two extra arguments — so sglang-jax's kernel is validated against
tpu-inference's independent pure-JAX reference. See
[`profiles/native/ragged_paged_attention/report.md`](profiles/native/ragged_paged_attention/report.md).

The KV-cache update kernels perform **zero arithmetic**, so they are reported
as achieved HBM bandwidth and their `mxu_utilization_pct` is null rather than a
misleading zero. Both must match the pure-JAX reference *bitwise* — an
approximately-correct copy is a wrong copy. See
[`profiles/native/kv_cache_update/report.md`](profiles/native/kv_cache_update/report.md).

That directory also holds a second contract, `dsv4_compress_and_store`, and it
is the corpus's clearest case of a kernel that could only be validated by
**measuring** its data layout rather than deriving one.
DeepSeek-V4's compressor is not a copy: it projects hidden states into a
compressed KV state, scatters it, then at every `compress_ratio` boundary
RMS-norms, RoPEs and fp8-quantizes one record. Its two Pallas launch points sat
unvalidated for a day, because upstream publishes **no host-side readback** for
their packed cache — the slot-to-address math lives inside on-device
`BufferedRef` classes — and the only pure-JAX twin, `compressor.py`, packs into
a different layout entirely (`[pages, page_size//4, 4, 640]` against the Pallas
`[pages, physical_page_size, 4, 128]`). Re-deriving a packed layout is exactly
what this corpus refuses to do for references.

Measuring one is a different matter, and two one-token probes settled it:

- **The `SLOT_PACK` axis is a byte-plane axis.** Writing a single token of
  all-ones sets exactly 4096 bytes, and the only values present are 63 and 128 —
  the two nonzero bytes of a float32 `1.0`. So sub-slot *b* holds byte *b* of
  every float, the same "byte lane" packing `compress_norm_rope._to_byte_lane`
  uses elsewhere in the same codebase. Move that axis last, bitcast, done.
- **`slot_mapping` is in physical rows, not tokens.** Slot *S* occupies rows
  `[S, S + state_rows_per_token)` of page `S // physical_page_size`. Consecutive
  tokens must therefore be spaced `state_rows_per_token` apart; passing token
  indices makes each token overwrite all but one row of the previous one, and
  **nothing raises**.

Neither readback is assumed — both are self-checking. The state one round-trips
small integers *exactly*, which no wrong byte assignment does. The record one is
decided by an independent oracle: read row-major over the 512-byte row it agrees
**bit-exactly** with the pure-JAX twin's record, and read transposed it is off by
1e34. With those in hand, `proj_and_save_state` matches the reference over 128
slots to within 0.0255 against a bf16 ulp of 0.0402 — its matmul runs in bf16 on
the MXU, and an exact-float32 expectation is what made a correct readback look
wrong at first — and `compress_norm_rope_store` is bit-exact.

One trap survives and is pinned by a test rather than triggered by it:
`proj_and_save_state` hard-codes `tile_n = 128` while its `pallas_call` sets
`disable_bounds_checks=True`, so **a token count that is not a multiple of 128
hard-faults the chip** with a `virt_addr_translator_page_fault` rather than
raising — the process dies. Note also that `compressor_v1.py`, the only upstream
caller of either kernel, has no caller of its own anywhere in the pinned tree:
it is dead code upstream, which is why no test ships with it.


The quantized-matmul files each hold **two** kernels sharing one set of helpers,
so `blockwise_kernel.py`'s entry point is renamed on flattening to avoid
shadowing the per-channel one. Their upstream tuned-size tables contain no
bfloat16 activation entries at all, so the weight-only-quantized path is
untuned in both repositories — measurably so. See
[`profiles/native/quantized_matmul/report.md`](profiles/native/quantized_matmul/report.md).

**`topk_routing` is complete**: 5 of its 6 audited TPU launch points are
migrated and validated, and the sixth is excluded with the evidence recorded.

The router top-k kernels are **selection** kernels, so correctness is exact —
expert ids must match bitwise and weights to 0.0, since a nearly-right index is
a wrong index. Tokamax also ships a SparseCore top-k that runs on this v6e but
does not reproduce `lax.top_k` semantics under the obvious calling convention;
it is deliberately **not** in the corpus, with the evidence recorded in that
family's `baseline.py`. See
[`profiles/native/topk_routing/report.md`](profiles/native/topk_routing/report.md).

The directory also holds a fourth contract that is **not a router at all**.
DeepSeek-V4's `streamindex_topk` — the "lightning indexer" — scores every
compressed KV position against each query token and returns *kv positions*
rather than expert weights. Its score is `sum_h relu(q_h · k_s) * w_h`, with the
ReLU **before** the head sum, which is what makes it a DSA indexer rather than
an attention score, and it reads an fp8 cache with ue8m0 block scales packed
inline with the keys. Two preconditions are pinned by tests because neither
announces itself: `k` must be a multiple of 128, and **`seq_lens` is in
uncompressed units** — the kernel divides by `compression_ratio` itself, so
passing an already-divided length does not raise, it silently retrieves from a
prefix.

Both repositories ship it, and the copy is **verbatim**: comparing the two after
`ast.unparse` and dropping docstrings, 10 of 10 shared definitions match except
one, which differs only in spelling a comparison the other way round
(`0 <= old_seq_idx` versus `old_seq_idx >= 0`). They also agree bitwise on
output. Both are counted, following the grouped-matmul precedent where
sglang-jax's kernel is likewise the same code as tpu-inference's — these are two
upstream lineages that can diverge, and the corpus records the measurement
rather than picking one. Contrast the splash-attention call, where MaxText's
copy lives in a directory literally named `tokamax_splash_attention` and *is*
excluded. A test pins the equivalence, so a future divergence shows up as a
failure rather than as two silently identical rows.

**`mla_attention` is complete**: 6 of its 9 audited TPU launch points are
migrated and validated, and the other 3 are JAXBench's `3p_MLA_Attention`, which
contributes no new Pallas kernel — it is the flash-attention kernel already in
the corpus, applied at MLA shapes.

MLA compresses the KV cache into one latent stream shared by all query heads.
Its cache holds the latent and rotary parts **concatenated**
(`kv_dim = align(lkv,128) + align(r,128)`), and `cache_kv` is **donated** — a
benchmark loop needs a fresh cache per call. This family reports speedups
*between implementations* only: no pure-JAX reference here is jittable, and no
denominator was invented in its place.

The directory holds **five contracts, not one**. Two of them are dangerous in
the same way: what makes them different from their neighbours does not show up
in a signature.

**tpu-inference v2 takes the same nine argument names as v1 with `ql_nope`
transposed.** v1 wants `[num_tokens, num_q_heads, lkv_dim]`; v2 wants
`[num_q_heads, num_tokens, lkv_dim]` and returns head-major too, while `q_pe`
stays token-major in both. When the two axes differ in size v2's validator
raises; when `num_tokens == num_q_heads` nothing catches it and the kernel
returns a **wrong answer at cosine 0.534** against the reference, versus
0.99999 for the correctly transposed call. `baseline.nine_args_head_major`
exists so call sites do not open-code the transpose, and a test pins both
halves. This is also why v2 carries a second Pallas launch: it physically
transposes on entry and exit through `xpose_pipeline`, a `layout_transpose`
launch point that is inlined as a dependency and **not** counted as an MLA
migration. Upstream tests v2 only on an fp8 cache and comments that it "only
supports FP8 KV cache"; bf16 works too, and agrees more closely (0.99999 versus
0.996), because with fp8 the cache the kernel writes back is itself quantized.

That transpose module imports `sympy.divisors`, which is not in the pinned
dependency set, so the flatten substitutes a trial-division equivalent and a
test checks it against the brute-force definition for every *n* up to 2000. That
is a different judgement from the qwix deferral below, and the difference is the
point: qwix decides numerics and cannot be reproduced in a few lines, whereas
"the sorted divisors of a positive integer" is a definition and is used only for
host-side integer tile selection before any kernel runs.

**The two DeepSeek-V4 kernels are a pipeline, not alternatives.** `mla_swa`
runs the sliding window and returns `(out, cache, L, m)`; the sparse kernel's
`swa_accumution`/`swa_l`/`swa_m` arguments are exactly those three, rescaled
into its own online softmax. Upstream chains them with
`unnormalized_output=True` on the SWA call — a flag whose **default is False**,
which is the wrong value for chaining. Neither upstream test exercises the
chain, so a corpus test pins the default and the argument correspondence.

Both DeepSeek-V4 kernels read a **uint8 DSV4 FP8 cache**: a 640-lane page row
holding 448 bytes of `float8_e4m3fn` latent, 128 bytes of bfloat16 rotary, 7
`float8_e8m0fnu` block scales and 57 bytes of padding. `baseline.py` provides
`pack_dsv4_fp8_cache`, `unpack_dsv4_fp8_cache` and `quantize_dequantize_dsv4`
so a reference sees what the kernel sees.

Their references are ports of upstream's own test-file references rather than
corpus re-derivations — but **upstream's output comparisons are weaker than they
look, and one of them is vacuous.** In `mla_swa_test`, `attention_sinks` are
drawn from [200, 500] while the attention logits reach ~135, so `exp(sink − m)`
swamps the softmax denominator and every output on both sides collapses to
~1e-26: two arrays of zeros agree at any tolerance. Only `L`, `m` and the cache
carry that check. The sparse test has a milder version — its constant carry-in
pins the output near `5000/200 = 25` whatever the attention does. The corpus
therefore runs each kernel twice: once at upstream's settings, and once with the
sink at 0.0 (outputs at absmean 0.52) or a neutral carry-in (absmean ~10), where
the comparison actually constrains the attention math. Tests assert both the
degeneracy and the informative case, so neither can quietly become the only one.

See
[`profiles/native/mla_attention/report.md`](profiles/native/mla_attention/report.md),
and note the profiling caveat above — that report's numbers cannot currently be
regenerated.

**`ragged_paged_attention` is complete**: all 9 audited TPU launch points are
migrated and validated, with none excluded.

It holds **five** contracts, not one. The
context-parallel `rpa_v3_cp` shards the KV sequence across devices and
carries `cp_rank`/`cp_group_size`/`q_pos_offsets`; on this single-chip host
only its degenerate `cp_group_size=1` case is validated, and the ledger
says so rather than implying the sharded path was checked. sglang-jax's
`ragged_paged_attention.py` is not `rpa_v2` despite the filename: it takes the
same ten parameters as its own v3 file plus a `custom_mask`, over a **4-D**
fused KV cache with K and V interleaved on the head axis, where `rpa_v3` uses a
5-D packed layout. That 4-D requirement came from the kernel's own validation
code — the file's `get_kv_cache_shape` returns the 5-D shape and the kernel
*rejects* it, and upstream's only call site builds that same rejected shape, so
that benchmark is stale. A test pins both the working layout and the rejection.

`batched_rpa` is the corpus's **largest implementation by module count** — nine
upstream modules flattened in dependency order — and the only one carrying **two
launch points in one file**: a schedule-planning kernel runs first and decides
which (sequence, page) pairs each grid step handles, then the attention kernel
runs that plan. It batches work across sequences instead of looping per
sequence. A call lowers to **four** `tpu_custom_call`s, not two: upstream's
wrapper runs both launch points once for the decode region and once for the
mixed region.

It exposes **two KV layouts that are not interchangeable**.
`HEAD_ALONG_SUBLANE` is upstream's default and its cache shape is exactly
`rpa_v3`'s, which is what lets the v3 reference validate this kernel with no
conversion in between. `SEQ_ALONG_LANE` has its own shape and **requires
`page_size=128`** for tile alignment, rejecting anything else. Comparing the two
needs care: feeding each an independently-random cache of its own shape compares
different data and reports a spurious **cosine 0.097**. Setting
`kv_lens == q_len` makes the kernel write every KV token itself, so a zeroed
cache in either layout is comparable — and then both agree with the reference to
0.99998. `RpaCase.PREFILL` fails to compile on this host, identically flattened
and unflattened, so it is an upstream limit rather than a migration defect;
upstream's wrapper only ever calls DECODE and MIXED.

That kernel also produced the corpus's sharpest lesson about **flattening
itself**. It sat blocked for a session on a "JAX arrays are immutable" error
raised from inside a Pallas kernel, where the obvious reading was an upstream
bug. It was not: `batched_rpa/schedule.py` is a module named `schedule` that
also takes a parameter named `schedule`, and the flatten stripped `schedule.` as
a module qualifier everywhere, rewriting `schedule.s_idx[step, lane] = s_idx`
into `s_idx[step, lane] = s_idx`. That parses, imports, and passes every static
check the flatten script had — it fails only when the kernel runs, pointing at a
line that looks correct. The same blind regex had also been eating prose,
turning "for the RPA kernel." into "for the RPA ". `tools/flatten_gdn.py` now
strips qualifiers over the AST with a scope stack, skipping any name bound in an
enclosing scope and never touching comments or docstrings;
`tests/test_flatten_tools.py` pins the behaviour. Re-running every flatten that
used the old helper showed **only `batched_rpa` was affected** — `gated_delta_net`
and `gated_linear_attention` regenerate byte-identically — but the check is
worth repeating whenever a module name is also a plausible local.

**`splash_attention` is complete**: 10 of its 13 audited TPU launch points are
migrated and validated, and the other 3 are JAXBench's `4p_Sparse_Attention`,
which is the same kernel as its `2p_GQA_Attention` (28 of 31 definitions
AST-identical).

Splash attention is the corpus's **first family with migrated backward
kernels**, and the backward pair is validated by differentiating through the
kernel's `custom_vjp`. Two things are worth knowing before reading its numbers:
`BlockSizes.get_default()` is 128 in every dimension and carries an upstream
"TODO: select better parameters" — it is ~18× slower than JAXBench's autotuned
forward blocks — and upstream autotuned the **forward only**, leaving every
backward block `None`. See
[`profiles/native/splash_attention/report.md`](profiles/native/splash_attention/report.md).

**Not every splash kernel has three launch points.** JAXBench's and MaxText's
`attention/` copies do — forward, backward-dQ, backward-dKV — but the *Tokamax
lineage* has **two**: it fuses the dQ computation into the dKV kernel, whose
single `pallas_call` returns `dq_unreduced, dk, dv`. Tests pin the count on both
sides, so the asymmetry stays visible rather than reading as a missing
migration.

MaxText carries a second splash kernel under `kernels/tokamax_splash_attention/`,
and it was **excluded from the corpus until this family was audited** on the
strength of that directory name — "MaxText vendored copy of Tokamax splash".
Measured, the name is stale: only **7 of 20 shared top-level definitions are
AST-identical (35%)**, and the copy is 2098 lines against Tokamax's 2346. That
is *below* the 42% at which the corpus migrated both halves of the gdn v3 pair
as genuinely diverged, and nowhere near the 90% that justified excluding
JAXBench's `4p_Sparse_Attention`. The exclusion was inconsistent with every
other duplication call in the corpus, so it is lifted, both launch points are
migrated and validated, and a test pins the 35% measurement — if the two ever
converge back above 60%, that test fails and the question re-opens.

**`sparsecore_ragged_gather` is complete**: 10 of its 12 audited TPU launch
points are migrated and validated, and the two `ragged_scatter` kernels are
excluded because they return gather semantics under the obvious calling
convention.

The SparseCore ragged gathers are the corpus's **first non-TensorCore kernels**:
they launch through `pl.kernel` over a `plsc.VectorSubcoreMesh` and run on the
v6e's SparseCores, so the metric is achieved bandwidth, not MXU utilization.
Four gathers are **bit-exact** against `x[indices]`, which here is not a
reverse-engineered reference but upstream's own no-SparseCore fallback. The
gather-*reduce* kernels are close rather than exact, and for a structural
reason: they accumulate in fp32 and write bf16, so they land one bf16 ulp away.

The family holds **four contracts**, not two. Beyond `ragged_gather` and
`ragged_gather_reduce`, MaxText's `gather_reduce_pallas` takes positional
`op`/`idx` with keyword-only `reduce_group_size` and no `valid_rows_mask`, and
tpu-inference's `dense_gather_reduce` drops the mask and makes `topk_weights`
**2-D** `[tokens, reduce_group_size]` rather than one weight per gathered row.

**Every gather-reduce kernel here carries an undocumented precondition, and
three of them fail in ways that do not look like failures.** They are worth
listing, because between them they cover most of the ways a SparseCore kernel
can mislead you:

- MaxText's **v1** `ragged_gather_reduce` hard-codes 8 column partitions and
  derives everything else from that, which gives it a **shape floor**. At
  `indices.shape[0] >= 1024` it agrees with the reference to 0.0155. At 256 and
  512 it returns a **wrong answer** — relative error 1.0, disagreeing with its
  own `enforce_fallback` JAX path, which is exact at every size — and at some
  shapes it **halts the SparseCore outright**, killing the process. Its docstring
  mentions none of this.
- MaxText's **v2** replaces the hard-coding with a cost model and asserts
  `num_row_partitions <= num_simd_lanes`. A narrow `hidden_size` trips the
  assert; 2048 and up work. That one at least fails loudly.
- MaxText's `sc_gather_reduce` has three: it is **bf16 only** while its own
  error message says "must be f32 or bf16"; `M` must be divisible by 16384 at
  the default tiling; and `reduce_group_size <= 4`, because the output
  `BlockSpec` row dim is `(num_lanes // group) // packing`, which with 8
  SparseCore lanes and bf16 packing 2 is **zero** at `group=8`. `group=8` is the
  only value upstream's own `gather_reduce_sc_test.py` uses, so that test cannot
  pass on this v6e. Its default `col_chunk_size=3584` also overflows this
  device's 256 KiB SparseCore VMEM; 512 fits.

Tests pin all of these, and pin them **from the source** rather than by
triggering them — a SparseCore halt takes the whole test process down with it,
so a test that provoked one would be worse than no test.

MaxText's and tpu-inference's v2 gather-reduce files are a **diverged vendored
pair**: 14 shared definitions, 12 AST-identical (85%). Both are migrated and the
measurement recorded, as for the gated-delta-net v3 pair — and unlike the
streamindex top-k pair next door, which is verbatim.

Two cautions belong with their numbers. First, standalone timings understate
these kernels by construction: XLA's `x[indices]` already runs at ~1634 GB/s,
essentially HBM bandwidth, and a SparseCore gather's value is that it overlaps
with TensorCore work — a benchmark that leaves the TensorCore idle measures the
one regime where it cannot win. Second, `ragged_gather_reduce` **silently falls
back to XLA** when `x` fits comfortably in VMEM, so profiling it at a small
shape compares XLA against itself and reports a tie. `tools/profile_kernel.py`
now counts `tpu_custom_call`s in the lowered HLO and refuses to profile any
non-reference implementation that lowers to zero; every `result.json` records
`pallas_launches`.

Because a standalone timing is the wrong question for these kernels,
`tools/overlap_harness.py` measures the right one: it times a TensorCore
workload alone, a gather alone, and both compiled together with no data
dependency, and reports the gather's **marginal** cost. It also reads the
trace's separate TensorCore and SparseCore tracks to measure overlap directly
rather than infer it.

Both the workload you hide behind and the gather's dtype decide the answer, and
each one reverses it. Against a dense matmul with fp32 gathers the SparseCore
kernels cross over and win above ~12K rows; against the **grouped matmul an MoE
layer actually runs**, that crossover disappears and XLA is 16–33% cheaper
everywhere. Switch the gather to **bf16** — what an MoE layer actually carries —
and it reverses again: SparseCore wins at every size, by 10–27% against the
grouped matmul and up to 2.35× against the dense one. **The bf16-against-GMM row
is the one to use.**

The reason is not simply "half the bytes": standalone, every gather gets 2–27%
*slower* in bf16, so at `hidden=1024` these gathers are bound by per-row work
rather than bandwidth. What halves is *contention*, and only the SparseCore
gather collects that saving — XLA's runs on the TensorCore, where the sub-word
packing cost lands on the same unit doing the matmul.

Nor is the dense-vs-grouped difference about bandwidth, though it looked that
way: sweeping the grouped matmul across 14× of arithmetic intensity and 4× of
HBM utilization moves the result **not at all**, and a dense matmul at 16.3% HBM
and a grouped one at 15.3% give opposite verdicts. What separates them is
currently unexplained, and the report says so. Two further findings: the gather
is *fully overlapped in time* (0.98–1.00) even in the rows where it loses, so
concurrency was never the problem; and XLA **already offloads scatters to the
SparseCore** inside the grouped matmul, so it is not the idle unit the premise
assumes. See
[`profiles/native/sparsecore_ragged_gather/report.md`](profiles/native/sparsecore_ragged_gather/report.md).

Gated delta net is the corpus's first **state_space** family, and its reference
is upstream's own pure-JAX implementation rather than a corpus-written one. It
carries a warning worth repeating: the reference and the v1 kernels take
**byte-identical argument lists but disagree on a precondition** — the reference
applies `jax.nn.silu(mixed_qkv)` itself, the kernels expect it already applied.
Fed the same raw tensor they agree only to cosine **0.72**; fed correctly, to
**0.9999976**. Nothing in the shapes or types catches it, so `baseline.py`
records which side of the boundary each entry point sits on in `PRE_SILU_INPUT`
and a test pins the divergence.

**The SiLU precondition is not uniform even within one repository.** Four
tpu-inference entry points take the same leading arguments and make three
different choices: the reference and v2's `recurrent_scan` apply
`jax.nn.silu(mixed_qkv)` themselves, v1's wrapper expects it already applied,
and v2's decode path exposes an explicit `apply_silu` argument. Each was
established by measurement — the wrong choice runs and returns the right
shapes. v1 fed raw scores cosine **0.72**; `recurrent_scan` fed post-SiLU
scores **0.983**, close enough to read as a tolerance problem rather than a
contract error. `baseline.PRE_SILU_INPUT` records all four and tests pin them.

**gated_delta_net is complete**: all 9 of its audited TPU launch points are
migrated and validated. It holds **three contracts, not one**. v1's `ragged_gated_delta_rule` is
the recurrence alone; the v3 kernels fuse a depthwise causal conv1d with it and
carry *two* caches rather than one; and `triangle_solver` inverts unit lower
triangular matrices for the chunked scan. Each has its own upstream-authored
reference — except the triangular inverse, which is a plain mathematical
identity and is therefore checked against `jnp.linalg.inv`, an oracle upstream
had no hand in. That distinction matters: everywhere else in this family an
error shared between kernel and reference would go unnoticed. The v3 pair is also a **diverged vendored copy** — tpu-inference
`gdn/v3` and Tokamax `causal_conv1d_gated_delta_rule` share seven module names
and 24 definition names but only ~42% AST-identical bodies, yet agree
**bit-for-bit** on every output: the divergence is organisational, not
numerical. Both are migrated so that stays measured rather than assumed.

Gated linear attention is the same idea as gated delta net next door — an O(T)
recurrence rather than an O(T²) softmax — with a *scalar* per-head decay instead
of a rank-one delta update. Its two contracts do not substitute for each other:
KDA has per-channel gates and a `beta` delta term, Simple GLA a single decay per
head. Both references are again upstream's own.

Simple GLA's calling convention is not guessable from its signature — only
`cu_seqlens_dev` is accepted, head dims must be multiples of 128, batch must be
1, `g_gamma` is a **log** decay so a positive value overflows to nan, and the
fused decode **donates** its state buffer. Every one of those was found by
reading sglang-jax's own `lightning_backend` call sites after guessing failed,
and each is pinned by a test.

**The PallasBench sweep added 43 launch points across 19 new directories** —
more than a third of everything the corpus carries, collected in one pass
rather than family by family. That was possible because PallasBench is the one
source that is uniform by construction: every kernel file holds exactly one
`pallas_call`, is self-contained apart from a single `pallasbench.provenance`
import used only to decorate `__doc__`, and has a matching `jax_<task>` in
`pallasbench/baselines/jax_baseline.py` — a module whose own docstring promises
"pure JAX reference implementations ... no Pallas". The references and the
inputs are therefore upstream's on both sides, down to the integer dtypes
`one_hot` needs and the positive-domain ranges without which `log` and `rsqrt`
are nan.

Because the 43 are uniform, their ledger entries are **derived** from
`tools/pallasbench_tasks.json` rather than hand-written like every other entry
in `CORPUS_DIRECTORIES`. Forty-three hand-written notes would have been
forty-three restatements of the same three facts. The per-task semantic contract
is upstream's own one-line description from `pallasbench/provenance.py`, which
also records where PallasBench distilled each task from: `relu` from the JAX
Pallas quickstart, `silu` from Tokamax's gated-linear-unit kernel,
`transformer_block` from MaxText's decoder layers, `triangle_update` from
AlphaFold-style Pairformer. Four kernels carry an upstream-recorded `change`
(all the same `jnp.rsqrt` → `jax.lax.rsqrt` swap for JAX 0.10), reproduced
verbatim rather than summarised.

**Seventeen of the 43 do not compile at PallasBench's own declared shape on a
v6e**, and that is recorded rather than quietly fixed. They fail against two
different limits, which is worth separating because the fix differs. Eleven
exhaust **total** VMEM: a level-1 elementwise kernel like `relu` maps a whole
4096x4096 f32 array into VMEM at once, 64 MiB in and 64 MiB out, and the
compiler reports using 128.00 MiB of 127.94 MiB — `add` and `multiply`, with a
second input, ask for 192 MiB. The other six fit in VMEM but exceed the 32 MiB
**scoped** allocation, because of intermediates rather than operands: `softmax`
needs 37.02 MiB once its max/sum/exp pair is counted, and `triangle_update`
materialises a `(c, n, n, n)` outer product, 33.5 MiB at n=64, for 39.08 MiB.
Each of those kernels is validated at a reduced shape, with the native shape,
the shape actually run, and the measured reason all recorded in the kernel
file's `SOURCE` and in the baseline's `TASK_INPUTS`; a test asserts the two
agree and that exactly 17 tasks are in that state, so a future reduction cannot
be added silently.

**One task is excluded because it does not lower on TPU at all.**
`embedding_lookup`'s kernel body is `o_ref[...] = table_ref[idx, :]`, a vector
gather from a VMEM ref, which Mosaic rejects during tracing with `Cannot do int
indexing on TPU` — at every shape, before any memory question arises. Excluding
a kernel is a claim about the compiler and compilers change, so the exclusion is
*rechecked* rather than asserted: `test_the_excluded_task_still_does_not_lower`
reconstructs that one line and fails if Mosaic ever grows the support, which is
the signal to migrate it.

**The twelve kernels that contract on the MXU are held to bf16, not f32.**
`multi_head_attention` failed at upstream's own 1e-3 by a hair — 9 elements of
131072, max difference 0.0019 — and the temptation is to widen the tolerance and
move on. Measured against a float64 host computation instead: the kernel is
0.0035 off, upstream's JAX reference is 0.0029 off, and one bf16 ulp at that
magnitude is 0.0030. The same reference at `Precision.HIGHEST` lands at 2.3e-7.
So the residual is TPU's default matmul precision on *both* sides of the
comparison, and holding these twelve to 1e-3 would be asking bf16 for f32
answers. The tolerance is `2**-8` for exactly the kernels whose source contains
a contraction, and the measurement that justifies it is in the test file.

**Closing `cross_entropy`, `dense_matmul` and `gated_mlp` took three kernels
from three repositories, and each was blocked on something different.** These
were the last open launch points in any started family, left behind when the
PallasBench sweep opened three families PallasBench did not finish.

**Tokamax's linear softmax cross-entropy is the corpus's fourth backward pass,
and the only one whose two halves are not independent.** Logits are `[B, V]` —
at a real vocabulary, larger than everything else combined — and neither pass
materialises them. The forward blocks over B, H *and* V, accumulating across V
by the log-linearity of log-sum-exp, and returns `lse` so the backward can
recompute logits blockwise instead of storing them. So the backward takes `lse`
as an argument, and a test exercising only the forward would leave half the
contract unchecked; `test_both_launch_points_reach_pallas` checks each
separately.

Nothing in that file needed flattening — it imports only `jax` — but three
substitutions did, and each is asserted against upstream's exact text so an
upstream edit fails loudly rather than producing a file that quietly means
something else:

* **jaxtyping** annotations cannot simply be deleted. The module has no `from
  __future__ import annotations`, so `Real[Array, "B H"]` is *evaluated* at
  definition time and removing the import turns every `def` into a NameError.
  They become inert subscriptable stand-ins, which check exactly as much as
  jaxtyping does without its runtime checker installed: nothing.
* **pydantic** backs `Config`, whose fields carry `Field(ge=...,
  multiple_of=128)`. Swapping in the stdlib dataclass keeps the class and
  silently drops the validation, and those constraints are real — a block size
  that is not a multiple of 128 does not lay out on a TPU lane. They are
  reproduced as an explicit `__post_init__`: the same check, written as code
  instead of as metadata, and pinned by a test.
* **the pinned JAX** moved two spellings. `pltpu.TensorCoreMesh(axis_name=...)`
  is now built by `pltpu.create_tensorcore_mesh(...)`. And the backward's
  `out_type` now names `pltpu.HBM` explicitly: its `emit_pipeline` `out_specs`
  are whole-array HBM passthroughs, because the backward DMAs into those refs
  itself, and this JAX only honours that when the output ref is *already* in
  HBM — otherwise it tries to allocate a whole-array buffer there and Mosaic
  refuses outright. Naming the space makes explicit what upstream's own
  `out_specs` already asked for.

**JAXBench's `8p_GEMM` needed no transformation at all** — it imports only
`jax`, `functools` and the public Pallas namespaces — but it is a reminder that
the reference is part of the contract. JAXBench ships `baseline.py` beside
`optimized.py`, and that file's `create_inputs` scales the second operand by
0.02. A corpus-written `jnp.dot` reference would have been comparing against
different *numbers*, not a different implementation, so upstream's baseline is
carried as `jaxbench_reference.py` and a test asserts both files still generate
identical inputs. `kernel` is bound to `workload` rather than `matmul`, because
`matmul`'s `block_shape` is keyword-only with no default.

**sglang-jax's fused gated MLP had no test and no baseline upstream**, so the
reference came from its only caller, `models/glm5_moe.py` — and that file holds
something no signature reveals. `w_gu` is **not** `concat([w_gate, w_up])`:
`post_load_weights` reshapes both to `(hidden, num_blocks, b_inter)` and
concatenates on the *last* axis, so gate and up interleave **per block**. The
kernel depends on it, slicing both halves out of one `(b_seq, 2*b_inter)` VMEM
tile. A reference built on the obvious concatenation computes a different
function and fails in a way that reads as a kernel bug. Both upstream regions —
the packing, and the non-fused fallback that states what the fused kernel must
equal — are quoted in `sglang_jax_reference.py` by *extraction* rather than
transcription, so the quotation cannot drift from the code it claims to
reproduce. And because a claim like that should be falsifiable,
`test_the_packing_is_not_plain_concatenation` feeds the kernel the naive
concatenation and asserts the answer changes.

Two things about that kernel are validated less than fully, and are recorded
rather than glossed. It ends in `jax.lax.psum` over a "tensor" mesh axis
because `wd` is sharded on its contracting dimension; this corpus runs it on a
one-device mesh, where that psum is the identity — the fusion, the pipelining
and the packed layout are exercised, the cross-shard reduction is not. And
upstream's `from jax import shard_map` call passes `check_rep`, which in the
pinned jax 0.10.2 is the *legacy* API's argument; the import is repointed to
`jax.experimental.shard_map`, which still ships and still takes it, rather than
translating `check_rep` into `check_vma` — the two flags do not mean the same
thing, and guessing which upstream wanted would be inventing intent.

**`layout_transpose` is the corpus's only deliberate duplication of a kernel,
and migrating it turned up a silent flatten defect.** Its three launch points
all move data rather than compute on it: `xpose_full` maps a whole array into
VMEM and transposes it, `xpose_pipeline` tiles and double-buffers for arrays
that will not fit, and `pin_vmem_custom_call` is an *identity* kernel whose only
purpose is the side effect — its output is a VMEM-resident buffer, so a later
consumer does not pay to fetch it. Because they relocate elements rather than
round them, every check here is **bitwise**, not a tolerance.

`xpose_pipeline` was already in the corpus before this family was: MLA v2 takes
head-major operands and physically transposes on entry and exit, so it cannot
run without it, and `tpu_inference_v2_optimized.py` inlines it as a dependency
that is *not* counted as an MLA launch point. Two copies invite drift, so
`test_the_mla_copy_has_not_drifted_from_this_one` compares them by AST — and it
failed the first time it ran.

The inlined copy had **lost its `@jax.jit(static_argnames=[...])` decorator**.
`ast.get_source_segment` on a `FunctionDef` starts at `def`, not at the
decorator above it, so `flatten_mla.extract_functions` had been dropping
decorators from every function it inlined — silently, because nothing failed: a
decorator-less `xpose_pipeline` still works when called from inside an
already-jitted MLA kernel. It was only visible by comparing two copies of the
same function. `extract_functions` now carries decorators, and restoring this
one exposed a second-order problem worth recording: extracted blocks land
*above* the flattened kernel that supplies the imports, and a decorator is
evaluated at definition time rather than at call time, so `@jax.jit` turned the
file into a `NameError` on import until the extracted block carried `import jax`
of its own. All six MLA files regenerate; five are byte-identical and v2 differs
by exactly the restored decorator and that import.

The rest of the family is checked against upstream's own
`tests/kernels/transpose_test.py` — its shapes, its axes, its float8_e4m3fn
dtype — including the two cases it added for specific failures: a 128x2048x256
array too large to load into VMEM whole, which is what separates
`xpose_pipeline` from `xpose_full`, and a bf16 384x128x512 transpose that needs
~33.6 MiB of *scoped* VMEM and so fails against XLA's 32 MiB default while
sitting comfortably inside total VMEM. That second one is the same distinction
the PallasBench sweep had to draw, and here upstream solves it with
`vmem_limit_bytes` on the single `pallas_call` rather than a global flag.

One detail of this kernel is worth knowing before calling it: **tile sizes are
requests, not commands.** `prev_closest_valid_divisor` lowers `n_tile` to the
largest divisor of the axis that is also a multiple of the dtype's sublane
packing — for fp8 that is 32, so a requested 160 against a 448-row axis becomes
64 — and it **raises** when no such divisor exists rather than quietly using a
non-divisor tile that would leave rows unprocessed. Upstream's own tables for
that chooser, including the shapes on which it must raise, are carried as tests.

**`fused_moe` is where carrying upstream's reference stops being a principle
and starts being the only workable option.** Three kernels, three repositories,
and "mixture of experts" turns out not to name a single function: routing can be
plain or grouped top-k, logits softmaxed or sigmoided or used raw, top-k weights
renormalised or not, the activation silu / gelu / clamped SwiGLU, the weights
sub-channel or per-channel quantised, a shared expert present or not. These
three files disagree on several of those. A single corpus-written reference
would have been checking one of them and quietly mis-checking the other two.

It costs nothing, because each file already ships its own pure-JAX `ref_moe`
beside its kernel, needing only two or three small helpers — so `baseline.py` is
built by extracting `ref_moe` and its transitive dependencies from all three,
renamed per source since all three are called `ref_moe`. The *inputs* are
upstream's too, extracted the same way from each kernel's own test file. That
matters more than it sounds: `gen_moe_inputs` is not a neutral generator, it
builds gating logits with a strictly decreasing per-token boost so the top-k
ordering is unambiguous, which is what makes a routing comparison meaningful
rather than tie-dependent.

**Two of the three are called `fused_ep_moe` and are not the same kernel.** The
corpus has been wrong about this shape of thing in both directions before — the
gdn v3 pair *is* a vendored copy, the splash pair is not — so it is measured
rather than assumed, by a test: of the seven top-level names sglang-jax's v1 and
tpu-inference's v1 share, only the three smallest (`align_to`,
`broadcast_minor`, `swigluoai`) are AST-identical, while `_fused_ep_moe_kernel`,
`fused_ep_moe` and `ref_moe` all differ. Their signatures differ too, which is
the more useful fact: tpu-inference takes `w1` with gate and up **fused on axis
1**, shape `(E, 2, H, I)`, plus raw `gating_output` it routes internally;
sglang-jax takes three separate weights and routing computed by the caller. So
they carry separate contracts, not one contract with a duplicate note.

Two things had to be worked out rather than read off. The sglang kernels want
`topk_weights`/`topk_ids` precomputed, and upstream's tests get them from a
flax `TopK` layer that is not in the pinned dependency set — so the corpus
derives them with `lax.top_k`, and rather than leave that as a comment,
`test_the_routing_agrees_with_the_reference` asserts the derivation reproduces
what `ref_moe` computes internally, exactly. And **v2 is its own
parameterisation, not a variation on v1's**: a four-field block config instead
of nine, a generator returning eight arrays instead of eleven, a `ref_moe`
taking precomputed routing instead of raw gating, and a smaller default shape.
Assuming otherwise is what broke this test on its first run.

One property is recorded rather than smoothed over: **sglang v2's `ref_moe` is
eager-only.** It forces a traced scalar to a concrete value, so it does not
survive `jax.jit` at all. That is upstream's, not something the flattening
introduced, and it means the usual "lower it and count `tpu_custom_call`s"
check cannot be run on that one reference; its Pallas-freeness is checked
structurally over the whole module instead. A test pins the limitation itself,
so if a future JAX makes it traceable the weaker check stops being necessary
and says so by failing.

All three are validated at **ep_size 1**. On a one-device mesh the dispatch to
expert-holding devices is local, so the routing, the fused activation and the
blocking are exercised and the cross-device collective is not.

And the vacuity sweep immediately earned its keep on this family, against a
comparison written for it. Upstream's tolerance is a flat `atol = 2e-1`, which
is reasonable at the scales its v1 tests reach — and vacuous at the scale its
own v2 test reaches, where the output peaks at 0.096. A kernel returning
nothing but zeros would have passed. Measured, all six comparisons here sit at
about **0.6% relative error** (worst ratio 0.0057), so the corpus applies
upstream's 2e-1 *relative to the reference's peak* instead: far looser than the
kernels need, and no longer satisfied by zeros. `close()` now also asserts
directly that zeros would fail, rather than leaving that to the next sweep.

**`speculative_decoding` is the corpus's first family that is control flow
rather than arithmetic** — three kernels that walk a draft token tree — and the
first where the three launch points needed three genuinely different kinds of
evidence, because upstream's own coverage of them is that uneven.

Nothing here has a tolerance to hide behind. Every output is an integer index,
count or mask, so every check is **exact equality**: a tree walk is either right
or it visits the wrong node.

**`verify_tree_greedy` has a live upstream oracle**, and passes it. sglang-jax
fixes a two-request tree by hand and asserts the exact integers coming out;
those vectors and expectations are carried into `baseline.py` as data, with the
upstream test quoted by extraction so the transcription cannot drift. A second
test asserts the oracle is not satisfied by an empty walk — the integer
analogue of the vacuity sweep the float comparisons get.

Running it turned up something the oracle itself gets wrong. The test passed
alone and **failed in the full suite**, with two slots of `predicts` coming back
as `8, 9` where upstream expects `0` — and `8, 9` are the second request's draft
tokens. `predicts` is an **output-only** buffer: the argument of that name
supplies only shape and dtype, `out_shape` allocates a fresh array, and the
kernel writes only the slots on the accepted path. Everything else is whatever
that SMEM allocation happened to contain. Upstream's expected vector spells out
zeros for those slots, which held on the run that produced it and does not hold
once anything else has run in the same process — bisecting, `fused_moe` or
`topk_routing` beforehand is enough to change them. So the corpus asserts the
two fully defined outputs exactly and `predicts` at the indices the kernel
actually writes, with a second test pinning that split: if a future kernel began
zeroing its whole output, upstream's full vector would match again and that test
would fail, prompting the wider assertion to come back.

**`build_eagle_tree_structure` has no upstream correctness test at all**, only a
performance benchmark. Writing a reference for it would mean guessing sglang's
own `retrive_next_token` / `retrive_next_sibling` encoding, which is precisely
the guess that produces confident, wrong failures. So it is checked two ways
that need no guess. First, the traversal invariant: whatever numbering is used
internally, walking first-child-then-sibling from the root must reach each of
the `draft_token_num` nodes exactly once and terminate — a tree, not a forest
and not a cycle. Second, by **composition** — its three routing outputs are
exactly the inputs `verify_tree_greedy` takes, and that kernel *does* have an
oracle, so the pair is run in series with a target that agrees with every draft
token. Making that agreement mapping-independent took a second attempt: setting
each row's argmax to its own drafted token assumes `retrive_index` is the
identity, which it is not, so the test instead makes *every* candidate the same
token. One gap is recorded rather than papered over: the packed `tree_mask`
byte layout is not checked, because nothing upstream defines it independently.

**`tree_speculative_sampling_target_only` does not run** — and the interesting
part is that this is upstream's defect, not the flattening's. sglang-jax's own
test for it is dead code: the body begins `return`, above the comment "this
kernel still have some problems". Fed the vectors left behind that `return`, the
kernel raises `TypeError: scan body function carry input and carry output must
have the same pytree structure` — and loading **upstream's unflattened file
directly**, with a synthetic module standing in for its one repo-local import,
raises the identical error. So the file is carried, because the corpus records
the state of the art rather than only its working parts, but it is counted as
**zero migrated launch points** with `correctness: UNVALIDATED`. A test pins the
failure, so an upstream fix will announce itself as a test that starts passing
rather than as silence.

Two of these three wrappers are also **eager-only**: they size their output
buffers from input *values*, so tracing them raises `ConcretizationTypeError`.
That is upstream's design — they are host-side wrappers, not jittable functions
— and it means the launch count has to be taken with their arrays closed over
rather than passed in.

**`paged_attention` looked like two launch points and is one.** sglang-jax's
`paged_attention/paged_attention.py` is a **GPU kernel** — it passes
`plgpu.CompilerParams(num_warps=..., num_stages=...)` unconditionally, Mosaic's
TPU lowering asserts it was handed *TPU* compiler params, and its own test file
opens with "This test suite is designed to be executed on GPU". The audit had
been counting it as a TPU candidate because its import is spelled `from
jax.experimental.pallas import triton as plgpu` while the backend check looked
for the dotted `jax.experimental.pallas.triton`. That check now reads parsed
imports; one launch point moved from portable to gpu, and the corpus's headline
went from 157 TPU-compatible to 156.

What remains is JAXBench's, and it needed **two reconciliations that appear in
no signature** — both now pinned by tests rather than left as prose:

**The kernel takes pre-scaled Q.** It has no `sm_scale` parameter and applies
none; the baseline applies `head_dim ** -0.5` internally. Fed raw Q, the two
disagree by 2.9 against a reference peaking at 0.14 — not a tolerance failure, a
different function. Pre-scaled, the difference is 0.0015. The test asserts the
*size* of both, so a kernel that started scaling internally would fail rather
than silently swap which call is correct.

**JAXBench's own two files disagree here**, which is the part worth flagging.
In `8p_GEMM` the `optimized.py` / `baseline.py` pair is drop-in, and a reader
who generalises from that would be wrong twice over: this baseline takes a sixth
argument (`cu_q_lens`, trivially `arange(num_seqs + 1)` in decode) and lays out
KV pages as `(total_pages, page_size, num_kv_heads, head_dim)` against the
kernel's `(num_kv_heads, total_pages, page_size, head_dim)`. Both are
relabellings, applied explicitly. And since JAXBench's own `workload` does not
pre-scale either, upstream's two files would not agree if anything compared
them — upstream only ever benchmarks them separately.

One further rename follows the pinned JAX: the kernel's six `pltpu.ANY` memory
spaces become `pl.ANY`, the current spelling of the same value.

## Profile on TPU

The profiling runner follows JAXBench's device-side timing protocol and keeps
wall-clock measurements only as diagnostics:

```bash
uv sync --frozen --group profile
export LIBTPU_INIT_ARGS="--xla_enable_custom_call_region_trace=true --xla_xprof_register_llo_debug_info=true"
uv run --frozen --group profile python tools/profile_kernel.py \
  --implementation jaxbench
```

It uses bf16 inputs, JIT compilation, 5 warmups, 50 profiled iterations,
Perfetto `jit_*()` device events, XLA `cost_analysis()`, and XPlane/XProf
per-operation summaries. The native upstream-shape comparison is in
[`profiles/native/flash_attention/report.md`](profiles/native/flash_attention/report.md);
the earlier common-shape flow validation remains in
[`profiles/flash_attention/report.md`](profiles/flash_attention/report.md).

## Provenance and licensing

**This corpus is a derivative work.** The kernels in `kernels/` are collected
from six upstream projects, all Apache-2.0, and most of each file is upstream's
code rather than this repository's. What is original here is the collection: the
flattening tools, the references and tests, the ledger, and the prose.

its `SOURCE` dictionary, and its docstring states what was changed to make it
standalone. Where an upstream file carried a copyright header, that header is
retained verbatim — 45 of the 108 do, which is exactly the set whose originals
had one; the flattening tools preserve leading comments and never add a notice
that upstream did not write.

`LICENSE` is Apache-2.0, matching every upstream. `THIRD_PARTY_NOTICES.md` lists
each project with the pinned commit its files came from. No upstream project
endorses this collection, and the project names are used only to describe where
code came from.
